Keccak GKR: What Is an "Instance" and What Does the Sumcheck Do?

A step-by-step walkthrough with concrete numbers. h=4 instances, showing one Keccak round.

1. What Is an Instance?

An instance is one independent execution of keccak-f[1600]. If you're hashing 4 different messages, you have 4 instances of the keccak-f permutation, each with its own 1600-bit input state and 1600-bit output state.

Each lane is a 64-bit word (u64). Lane A[x,y] of instance i is a specific u64 value. We want to prove: "applying one Keccak round to the input state gives the output state" — for ALL h instances simultaneously.

2. The Multilinear Extension (MLE)

To use the sumcheck protocol, we represent each lane as a polynomial. For h=4 instances with 64 bits per lane, we need n = 6 + log₂(4) = 8 variables.

For simplicity, let's use 4 bits and 4 instances, so n = 2 + 2 = 4 variables: (v₁, v₂) index the 4 bit positions, (v₃, v₄) index the 4 instances.

Lane MLE: A(v₁, v₂, v₃, v₄)

On Boolean inputs: A(b₁, b₂, b₃, b₄) = bit ⟨b₁b₂⟩ of lane in instance ⟨b₃b₄⟩

Example: A(1, 0, 0, 1) = bit 2 of instance 1
          (because ⟨1,0⟩ = 2 and ⟨0,1⟩ = 1)

Concrete values for one lane (say A[0,0]):

Instance (v₃,v₄) u64 word bit 0 (0,0) bit 1 (1,0) bit 2 (0,1) bit 3 (1,1)
inst 0 (0,0) 0b1101 1 0 1 1
inst 1 (1,0) 0b1010 0 1 0 1
inst 2 (0,1) 0b0011 1 1 0 0
inst 3 (1,1) 0b0100 0 0 1 0

This table IS the MLE. On Boolean inputs, A(v₁,v₂,v₃,v₄) returns one of these 0/1 values. On non-Boolean inputs (random GF(2¹²⁸) points), the MLE interpolates — giving a "mixed" field element.

3. What the Sumcheck Proves

We want to prove: "applying chi+iota to the pre-chi state gives the output state." The polynomial identity (for one output lane, simplified):

Output[i,j](v) = PreChi[i,j](v) + PreChi[i+2,j](v) + PreChi[i+1,j](v) · PreChi[i+2,j](v) + RC

This must hold for ALL v on the Boolean hypercube {0,1}⁴
(= for every bit position in every instance)

The sumcheck protocol doesn't check all 2⁴ = 16 points directly. Instead, it reduces the check to a single evaluation at a random point:

Claim: Σv ∈ {0,1}⁴ eq(α, v) · f(v) = mixed_eval

where f(v) = Σi,j w[i,j] · chi_iota(input(v))[i,j]
and α = random GF(2¹²⁸) point chosen by verifier
and mixed_eval = Σi,j w[i,j] · output[i,j](α)

If the identity holds on all Boolean points, then by MLE uniqueness it holds at α too. The sumcheck protocol verifies this random-point evaluation interactively.

4. How the Sumcheck Executes (Round by Round)

The sumcheck has n = 4 variables. It binds one variable per round, starting from the last (highest instance variable) and working down.
In the GKR, only the 2 instance variables (v₃, v₄) are sumcheck'd. The 2 bit variables (v₁, v₂) are pre-collapsed at the boundary using bit_challenge. So we actually run 2 rounds, not 4.

R1 Sumcheck Round 1: bind v₄ (instance high bit)

Split instances into lo (v₄=0) and hi (v₄=1):

lo half (v₄=0)
Instance 0 (v₃=0, v₄=0): word = 0b1101
Instance 1 (v₃=1, v₄=0): word = 0b1010
hi half (v₄=1)
Instance 2 (v₃=0, v₄=1): word = 0b0011
Instance 3 (v₃=1, v₄=1): word = 0b0100

The prover computes f(v₁,v₂,v₃, z) for z ∈ {0, 1, ∞}, summing over (v₁,v₂,v₃):

y₀ = Σv₁,v₂,v₃ eq(α, v) · f(v₁,v₂,v₃, 0) [uses lo instances only]
y₁ = Σv₁,v₂,v₃ eq(α, v) · f(v₁,v₂,v₃, 1) [uses hi instances only]
y∞ = degree-2 coefficient [uses lo XOR hi]

This gives a degree-2 polynomial g₁(z) = c₀ + c₁z + c₂z²
The prover sends c₁, c₂ (2 field elements = 32 bytes)

Verifier checks g₁(0) + g₁(1) relates to the claim, then samples challenge r₁.

Now the fold happens: For each pair (inst 0, inst 2) and (inst 1, inst 3), compute the folded value at v₄ = r₁:

This is where bits become field elements. For bit 0: inst0 has bit=1, inst2 has bit=1 → folded = 1 + r₁(1-1) = 1
For bit 1: inst0 has bit=0, inst2 has bit=1 → folded = 0 + r₁(1-0) = r₁
For bit 2: inst0 has bit=1, inst2 has bit=0 → folded = 1 + r₁(0-1) = 1+r₁

Each bit became a different GF(2¹²⁸) value!
4 bits × 2 remaining instances = 8 field elements stored for the next round.
↓ now working on field elements, not bits ↓
R2 Sumcheck Round 2: bind v₃ (instance low bit)

Split the 2 remaining folded instances into lo and hi:

lo (v₃=0): folded inst 0|2
bits: [1, r₁, 1+r₁, 1+r₁]
hi (v₃=1): folded inst 1|3
bits: [r₁, 1, r₁, 1+r₁]

The prover evaluates the chi polynomial on these field-element blocks. This is the expensive part — each chi evaluation requires GF(2¹²⁸) multiplications (PMULL).

For each output lane (i,j):
  a = preChi_lo[i,j], b = preChi_lo[i+1,j], c = preChi_lo[i+2,j]
  chi_1 = a + c + b·c ← this "b·c" is a GF(2¹²⁸) multiply (PMULL!)

Each of the 4 "bit" positions requires its own PMULL. With 25 lanes × 4 bits = 100 PMULLs per instance pair.
(In reality: 25 × 64 = 1600 PMULLs per instance pair)

The prover sends c₁, c₂ again. Verifier samples r₂. Final fold produces one instance with 4 field elements.

↓
F Finish: dot product with bit_weights

The 4 remaining field elements are dot-producted with the bit_weights (Lagrange basis at bit_challenge) to produce 25 scalar evaluations — one per lane. These are the input lane evals that chain to the next Keccak round.

For each lane ℓ:
  eval[ℓ] = Σb=0..3 final_block[ℓ][b] × bit_weights[b]

= one GF(2¹²⁸) scalar per lane
= the MLE of lane ℓ evaluated at point (r₂, r₁, bit_challenge₁, bit_challenge₂)

5. The Full 24-Round Chain

Each Keccak round executes the sumcheck above. The output (25 lane evals at the reduced point) becomes the verifier's claim for the NEXT round:

Round 23: output claim on final state → sumcheck → 25 input evals = round 22's output evals
Round 22: output claim from round 23 → sumcheck → 25 input evals = round 21's output evals
  ...
Round 0: output claim from round 1 → sumcheck → 25 input evals = initial state evals

At the end: the 25 initial-state evals are checked against the committed input.

Total: 24 sequential sumchecks, each with log₂(h) rounds.
Each sumcheck round scans all remaining instances.
After the first fold of each sumcheck, every bit becomes a field element.
The bottleneck:
24 sumchecks × log₂(h) rounds each × scan all instances per round.
After the first round of each sumcheck, data is 64× larger (field elements vs bits).
This is why each Keccak round takes ~24ms uniformly — it's dominated by the GF(2¹²⁸) block-table scans in rounds 2 through log₂(h).

6. How the CircuitBuilder Avoids This

The CircuitBuilder doesn't prove "round(input) = output" as a polynomial. Instead, it expresses each AND gate as a constraint A & B = C, giving ~600 AND constraints per Keccak permutation.

CircuitBuilder AND constraint: A(z,X) · B(z,X) - C(z,X) = 0

z indexes the 64 bit positions within a word (6 variables)
X indexes the constraint (which AND gate, which instance)

Phase 1: collapse z (6 bit variables) into ONE scalar per word
    → Method of Four Russians: 8 byte lookups per word → 1 field element
    → Each word: 64 bits → 1 number. No 64× blowup.

Phase 2: sumcheck over X (constraint axis)
    → Each constraint is just 1 field element. Compact.
    → ONE pass over all 600h constraints. Not 24 sequential passes.

The CircuitBuilder can collapse bits first because its per-gate polynomial is simple: A · B - C — three values, one product. Easy to evaluate at 64 domain points.

The GKR's polynomial is chi(theta(rho(pi(input)))) — 25 lanes, rotations, XOR mixing, AND gates fused together. Evaluating this at 64 domain points is 64× more expensive than a single evaluation, which is why the "oblong" experiment regressed.
