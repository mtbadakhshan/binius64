GKR vs CircuitBuilder: How Bits Become Field Elements

A concrete example with 4 Keccak instances (h=4), showing ONE lane (1 of 25), tracking what happens to the 64 bits.
For simplicity we show only 4 bits (not 64) and use small numbers instead of GF(2^128) elements.

BOTH Starting Data: 4 instances, 1 lane, 4 bits each

Each instance has a u64 word for this lane. We show only 4 bits for clarity. In reality it's 64 bits × 25 lanes × h instances.

0 Raw u64 words (binary data)
Instance 0: 1 0 1 1 word = 0b1101 = 13
Instance 1: 0 1 0 1 word = 0b1010 = 10
Instance 2: 1 1 0 0 word = 0b0011 = 3
Instance 3: 0 0 1 0 word = 0b0100 = 4
Total: 4 instances × 4 bits × 1 bit = 2 bytes of data. In reality: h × 64 × 25 × 1 bit. At h=16384: 3.2 MB.
GKR Fused Round Prover
1 Sumcheck Round 1: fold instances (from words)

Split into lo={inst 0,1} and hi={inst 2,3}. Verifier sends challenge r1 = α. Each BIT folds independently: folded[bit] = lo[bit] + α × (hi[bit] - lo[bit]).

bit 0: inst0=1, inst2=1 → 1 + α(1-1) = 1
bit 1: inst0=0, inst2=1 → 0 + α(1-0) = α
bit 2: inst0=1, inst2=0 → 1 + α(0-1) = 1+α
bit 3: inst0=1, inst2=0 → 1 + α(0-1) = 1+α
Folded inst 0|2: 1 α 1+α 1+α
Folded inst 1|3: α 1 α 1+α
Key moment: Each bit is now a GF(2128) element (like "α" or "1+α").
1 word (4 bits) → 4 field elements = 4 × 16 = 64 bytes 32× blowup!
(In reality: 64 bits → 64 × 16 = 1024 bytes. That's 128× blowup.)
↓
2 Sumcheck Round 2: fold again (on field blocks)

Now each "instance" has 4 field elements. Fold with challenge r2 = β. Each position folds: result[bit] = lo[bit] + β × (hi[bit] - lo[bit]).

bit 0: 1 + β(α - 1) = 1 + β(α+1)
bit 1: α + β(1 - α) = α + β(1+α)
bit 2: (1+α) + β(α - (1+α)) = (1+α) + β(1)
bit 3: (1+α) + β((1+α) - (1+α)) = 1+α
Final (1 inst): 1+β(α+1) α+β(1+α) 1+α+β 1+α
Still 4 field elements. The dot product with bit_weights gives one scalar = the MLE evaluation.
GKR summary: After round 1, each bit became a full GF(2128) element. Round 2 operates on 4 field elements per instance = 64 bytes each.
All subsequent rounds work on this bloated representation.
At h=16384: round 2 scans 8192 × 64 × 16 = 200 MB.
CIRCUIT AND Reduction (Phase 1 → Phase 2)
1 Phase 1: Collapse bits FIRST (univariate skip)

Before folding instances, compute the weighted sum of all 4 bits in each word using Lagrange weights w0, w1, w2, w3 at the challenge point z.

Lagrange weights at z: w = [w₀, w₁, w₂, w₃]

inst 0: bits=[1,0,1,1] → 1·w₀ + 0·w₁ + 1·w₂ + 1·w₃ = w₀+w₂+w₃
inst 1: bits=[0,1,0,1] → 0·w₀ + 1·w₁ + 0·w₂ + 1·w₃ = w₁+w₃
inst 2: bits=[1,1,0,0] → 1·w₀ + 1·w₁ + 0·w₂ + 0·w₃ = w₀+w₁
inst 3: bits=[0,0,1,0] → 0·w₀ + 0·w₁ + 1·w₂ + 0·w₃ = w₂
After Phase 1: w₀+w₂+w₃ w₁+w₃ w₀+w₁ w₂
Key moment: Each word collapsed to ONE field element.
1 word (4 bits) → 1 field element = 1 × 16 = 16 bytes 4× blowup only!
(In reality: 64 bits → 1 × 16 = 16 bytes. That's 2× blowup. vs GKR's 128×.)
↓
2 Phase 2: Fold instances (on compact data)

Now each instance is just ONE field element. Fold with challenge r1 = α.

lo = [w₀+w₂+w₃, w₁+w₃], hi = [w₀+w₁, w₂]

fold 0|2: (w₀+w₂+w₃) + α((w₀+w₁) - (w₀+w₂+w₃)) = one number
fold 1|3: (w₁+w₃) + α(w₂ - (w₁+w₃)) = one number
After fold: scalar₀ scalar₁
2 instances × 1 field element each = 32 bytes. Clean, compact.
↓
3 Fold again → done
Final: ONE scalar
CircuitBuilder summary: The bits are collapsed to one scalar per word before any instance folding.
Phase 2 works on 1 field element per instance = 16 bytes each.
At h=16384: Phase 2 scans 16384 × 16 = 0.25 MB.

Why the GKR can't do Phase 1 first:
The CircuitBuilder's Phase 1 evaluates a simple polynomial per word: A·B - C (three lookups + one multiply).
The GKR's polynomial is chi(theta(rho(pi(input)))) — 25 lanes, rotations, XOR mixing, AND gates. Evaluating this at 64 or 128 points on the bit-axis domain costs 64-128× the work, which makes the "skip" more expensive than just doing the standard fold.

Bottom line: The CircuitBuilder pays 1× to collapse bits, then does everything on compact data. The GKR pays 1× for the first round (words), then 64× for ALL remaining rounds (field blocks).
